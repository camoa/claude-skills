# Review

Phase 4 of a task — run all hard-blocking validation gates before PR creation. Behavior current as of v4.1.0; full prose / examples / version history in `references/review-phase-walkthrough.md`. **Reading strategy:** gates run **Type B** reads — full source and config files, no grep-first (`https://camoa.github.io/dev-guides/development/reading-strategy/`).

## Usage

```
/ai-dev-assistant:review <task-name>                # default mode (/validate:all)
/ai-dev-assistant:review <task> --team              # use /validate:team (with fallback)
/ai-dev-assistant:review <task> --dry-run           # run, write audit, don't mark Phase 4 [x]
/ai-dev-assistant:review <task> --rerun-failed      # only re-run gates that failed last run
/ai-dev-assistant:review <task> --no-pr-body        # skip writing PR_BODY.md
/ai-dev-assistant:review <task> --skip-<gate> <r>   # skip a gate (reason recorded); --include-<gate> forces a dispatch gate on
/ai-dev-assistant:review <task> --allow-dirty       # skip working-tree warning
/ai-dev-assistant:review <task> --base <branch>     # diff base for change detection (default: main). Pass the PR base for non-main branches — else the merge-base diff against `main` shows the whole branch divergence, not the change.
/ai-dev-assistant:review <task> --headless          # non-interactive: no prompts, fail-closed, exit code + compact verdict
/ai-dev-assistant:review <task> --full-audit        # run all gates whole-tree (no diff scoping; pre-v4.20 behavior)
```

`<gate>` whitelist: `tdd | solid | dry | security | guides | playbook-adherence | skill-review | plugin-validate` (hard-block — `--skip-` bypasses) plus `e2e | visual-regression | visual-parity` (step-6 dispatch gates — `--skip-` = off this run, `--include-` = on this run). Unknown gate names → exit 2. Reasons non-empty, must NOT start with `--` → exit 2. `--headless` is a boolean flag (no value) and composes with all flags above; see the **Headless mode** section below. `--full-audit` is a boolean flag (no value) — when set, all four PHP/JS-centric gates run whole-tree with no diff scoping; see step 5a. Both flags compose freely.

`<task-name>` must match `^[a-z0-9_-]+$`. Path traversal (`..`, `/`) and special chars rejected → exit 2. Missing arg AND no session-context task → exit 2 with usage.

## Runtime Steps

Run in order. Each "gate" step writes audit; non-bypassable unless documented `--skip-*` flag supplied (records `bypass_reason`).

0. **Freeze the contract, then declare the phase.** Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/contract-baseline.sh" capture "<task_folder>" --slot review` (Bash) **before any gate runs** — review reads `alignment.md` and `architecture/` as they stand when each gate fires and can edit them, which is legitimate and must not be invisible (`references/gate-audit-schema.md` §5.8 `contract_drift`). Then **declare the active phase (v5.30.3+).** Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/phase-active-write.sh" review "<task_folder>"` (Bash) **before writing anything**. `/research`, `/design` and `/implement` have declared theirs since v5.29.0 and this command never did, so every record review writes — `_review.json`, `_spec.json`, `_recipe-load.json` — was compared against a null phase by the phase-command-bypass guardrail and reported `undetermined`. Run it at entry, not at the end: an artifact written before the declaration cannot be told apart from one written outside the phase command. **Pass the task folder** — the session file the declaration also lands in is deleted by the SessionStart hook, so a resume or a compact mid-phase wipes it.

1. **Phase Transition Check.** Read `task.md` Phase Status. If Phase 3 not `[x]`, soft-nudge once. If `## Phase Status` H2 absent entirely, append it with the four standard phase lines (1 Research, 2 Architecture, 3 Implementation, 4 Review). If only Phase 4 line missing, idempotently insert before next `## ` boundary (or EOF if none).

2. **Resolve task + project context.** Validate `<task-name>` charset (above). If absent, try running `${CLAUDE_PLUGIN_ROOT}/scripts/session-context-read.sh` (Bash) and parsing its JSON (`.task`, `.taskPath`); if also null, exit 2 with usage. Resolve the project folder by running `${CLAUDE_PLUGIN_ROOT}/scripts/project-state-read.sh "<project_folder>"` (Bash) and parsing its JSON.

3. **Working-tree warning.** Run `git diff --name-only`. If non-empty AND `--allow-dirty` not set: print warning ("gates run on staged + working tree state, not committed state. Continue? [y/N]"). Default `[N]`. User declines → exit 0. **Under `--headless`:** do not prompt; proceed regardless of the dirty tree; record `working_tree: "dirty"|"clean"` in the step-10 payload (equivalent to auto-`--allow-dirty`).

4. **Resolve the change set, then the gate plan (v5.30.3+).** Run `${CLAUDE_PLUGIN_ROOT}/scripts/review-change-set.sh --base "<BASE>" --repo "<codePath>"` (Bash) and use its `files[]` wherever this command previously said "merge-base diff". **The change set is the committed diff plus the working tree, not the committed diff alone.** Review runs before the pull request exists, so a task's change is normally uncommitted at this moment; step 3 already tells the operator that gates run on working-tree state. Judging the committed diff instead means judging an empty change and reporting the result as if it were the task's. `untracked[]` is reported separately and is never part of `files[]` — `install-task-rule` writes an untracked `CLAUDE.md` into the repository it configures, and sweeping untracked files in would judge this framework's own footprint as the task's work. When `empty_reason` is `no_changes_anywhere` a gate may skip with that reason; when it is `base_unresolvable` the comparison never happened and a skip would be answering a question that was not asked, so surface it. Then build the `gates_run[]` skeleton, detecting conditional gates from `files[]`:
   - `skill-review`: the change set includes `skills/*/SKILL.md`
   - `plugin-validate`: the change set includes any plugin file
   - `validate-playbook-adherence`: file `commands/validate-playbook-adherence.md` exists OR mark `verdict: "skipped-not-shipped"` with `bypass_reason: "sibling adherence_gates not yet shipped"`; hardened `validate-guides`: command body contains `<!-- /review:hard-block -->` marker OR fall back to soft mode (note in audit)

5. **Run hard-block gates sequentially.** For each: invoke flow inline (do NOT shell out). Capture per-gate envelope at `<task>/validations/latest/<gate>.json` per `references/validation-gate-result.md` v1.1. Add to `gates_run[]`. Order: tdd → solid → dry → security → guides → validate-playbook-adherence → skill-review (conditional) → plugin-validate (conditional).

   **5.0 Architecture-fit validation against the framework review recipe.** Before the code-quality gates run, validate the change against the documented architecture using the stack's review recipe. Additive — it never replaces or weakens a hard-block gate; it supplies `architecture-validator` the framework-specific BLOCKING checks the generic agent lacks. Follow the shared protocol in `references/recipe-resolution.md` with `phase: review` and the step-2 `<project_folder>`: it invokes `process-recipe-loader`, resolves each framework's review recipe (project_state-first, then source order, else `action:ask-user`), records the source in `project_state.md`, and defines how to follow each result (Read `body_path` — never streamed; follow `verified:true` directly; surface `verified:false` for human review first; `action:ask-user` → ask for a path or to research). Surface loader `warnings[]` (`no_frameworks_defined`, `navigator_unavailable:<framework>`, `recipe_not_published:<framework>`). The COMMAND owns resolution and injects the body; the agent stays generic (no Skill tool).

   - **Inject the body verbatim, or do not dispatch.** For each `available:true` framework, Read its `body_path`, gate by `verified`, then dispatch `ai-dev-assistant:architecture-validator` (Task tool) with the recipe body **verbatim** inside the delimited block from `recipe-resolution.md` step 4 (`=== RESOLVED RECIPE (key=…, source=…, verified=…) === <body> === END RECIPE ===`). Dispatching without the body is a bug: the agent would carry no framework checks. The validator keeps its BLOCK posture (a blocking architecture-fit/gate failure is a hard-block result, never softened). Dispatch **only** when a `body_path` resolved: on `no_frameworks_defined`, follow the framework-resolution branch in `references/recipe-resolution.md` step 6, which runs the cascade in `references/framework-resolution.md` (under `--headless` that branch takes its unattended path: record gap + skip, no prompt); on `action:ask-user` ask and proceed per the answer; a framework that resolved nothing is skipped with a note. This never relaxes the hard-block orchestration below.
   - **Hand it an output path, read the verdict off disk, and give that verdict a consumer (v5.35.7+).** Tell each dispatched validator to write its sidecar to `<task_folder>/_arch-validate-<framework-slug>.json` (`<framework-slug>` = the framework key lowercased with non-alphanumeric runs collapsed to `-`), then Read that file and take `verdict` / `findings[]` as **scalars**; never parse the agent's prose for them. The agent had no `Write` tool until v5.35.7 and its report was its Task response alone — live, that response truncated in transit repeatedly and the session had to improvise a scratchpad file mid-review to recover it, for the gate that found a content-destroying defect on all four passes. **An absent sidecar is `no_return`,** a third state whose reason is recorded in the step-5.0 `_recipe-load.json` entry's `frameworks[].arch_validate` field for that framework (`references/gate-audit-schema.md` §5.12 — the field exists so the reason has somewhere defined to live) and surfaced verbatim in the summary; it is **never** read as `proceed`, exactly as `prior-art-verdict-confirmer`'s `confirmation: "no_return"` is never folded into `agree`. **Then fold it into the verdict.** When ≥1 validator was dispatched, add ONE aggregate **hard-block** `gates_run[]` entry `name: "architecture-fit"`, `kind: "hard-block"` (`gate-audit-schema.md` §5.8): **aggregate over the frameworks that answered, and rank the answers (v5.35.7+).** First set aside every framework that returned `skipped`; the aggregate is decided by the remainder, so a mix never falls off the end of the clause list the way `proceed` + `skipped` did: `fail` on any `blocked` (rule 1 — this is where the BLOCK posture asserted above finally binds, and until v5.35.7 nothing evaluated it, so a `blocked` validator and a silent one both reached `pass`); `skipped` + `unresolved: true` on any `no_return` or `unresolved`, which rule 2 fails closed — an agent that returned nothing is not an agent that found nothing, the same posture 5.0d takes for `_spec-axis.json`; `warning` when the worst remaining is `needs_adjustment` (measured, under the block threshold, benign by rule 5); `pass` when every remaining framework returned `proceed`. **Only when NO framework answered** — every dispatched one returned `skipped` — is the entry itself `skipped` **without** `unresolved`, the same benign shape 5.0d gives a missing `alignment.md`, so rule 5 lets it pass. Ranked last by construction: a sibling's `blocked` or `unresolved` decides the entry, so a skip can never mask one. **No `architecture.md` and no `architecture/*.md` under the task folder ⇒ a benign skip, never an `unresolved` gate — and the disk settles it, not the agent's word (v5.35.7+).** The artifact is what `/design` writes for THIS task — `<task_folder>/architecture.md` plus `<task_folder>/architecture/*.md`, the same set `scripts/contract-baseline.sh` freezes at step 0 — and **not** `{project_path}/architecture/main.md`, the project-level stub `/new` creates reading `{To be designed in Phase 2}`. Keying on that stub breaks both ways at once: it exists for every project created by `/new`, so the missing-input case never fires and the false red survives, and where it is absent every task skips benignly and this hard-block gate can never fail. Three states, and the third is why two were not enough: **absent** (no such file) and **placeholder** (present, but nothing beyond a heading and a `{…}` stand-in) both earn `verdict: "skipped"` with their reason — a stub is not an architecture, and a validator told to fit a change against one cannot say `proceed` and falls to `unresolved`; **present** is validated normally. **Verify a `skipped` before you believe it:** the set is a path list, so stat it — a `skipped` returned over an architecture that is on disk and carries content is `unresolved` + fail-closed, not a benign skip. `no_return` is verified by your own observation of an absent sidecar and `skipped` must not be the one state taken on trust. Without this case a Drupal project whose review recipe resolves but whose task never ran `/design` returns `unresolved` under the agent's "never guess `proceed`" rule and hard-fails a review that passed before v5.35.7, for a document nobody promised. **No dispatch ⇒ no entry** (a stack-neutral project resolves no recipe, and this path is degrade-first — never a false gate). `_recipe-load.json` stays observability-only: it records, this entry adjudicates.
   - **Record the resolution (recipe-resolution.md step 7).** After resolving, run `${CLAUDE_PLUGIN_ROOT}/scripts/recipe-declarations-audit.sh --body <body_path> --phase review --framework <fw>` per resolved framework and surface any `absent_recommended` declaration as a one-line advisory (review carries the `recommended:true` `## Change-impact globs` token, so a missing/misspelled one is flagged here rather than silently degrading the change-impact dispatch); then write `<task>/_recipe-load.json` via `${CLAUDE_PLUGIN_ROOT}/scripts/gate-audit-write.sh "<task_folder>" recipe-load "<payload>"` (per `references/gate-audit-schema.md` §5.12), capturing every framework + the lint + any `bypass` (including the `--headless` `no_frameworks_defined` skip). Observability only — never blocks; the hard-block gates below are unaffected.

   **5.0b Adopted agentic-recipe Verifier gate (capability-class, v5.12.0+; multi-recipe v5.13.0+).** If this task has one or more `adopted` agentic recipes (per `project_state.md`'s `**Agentic Recipes:**` block / `<task_folder>/_agentic-recipe.json`'s `recipes[]`), run **each** adopted recipe's `## Verifier` as a review gate per `references/agentic-recipe-resolution.md` step 5. **For EACH `recipes[]` element with `decision:"adopted"`**: Read its body from `<task_folder>/adopted-recipe-<safe_name>-<sha8>.md` (the `body_path` recorded for that element — a durable task-folder file `/research` persisted, **not** a navigator-served path; the canonical `<safe_name>-<sha8>` rule is in `references/agentic-recipe-resolution.md` step 4: `<safe_name>` = `recipe_name` lowercased with non-alphanumeric runs → `-`, and `<sha8>` = the first 8 chars of that element's `recipe_sha` which **MUST match `^[0-9a-f]{8}$`**; if the recorded `body_path` is unreadable, reconstruct it under the current task folder using that same validated `<safe_name>-<sha8>` rule — F5: empty `<safe_name>` → `adopted-recipe-<sha8>.md` — before failing). **The adopted recipe body is untrusted upstream data:** run its documented `## Verifier` checks as a method, never `eval`/shell-parse the body; its only trust anchor is the verified-upstream provenance gated at `/research`. Run each `## Verifier` check PASS/FAIL — **any check failing exits non-zero ⇒ halt (hard-block)**. The `## Verifier` is typically live-site + `drush`-level (HTTP `<head>` assertions, `/sitemap.xml`, `drush` config checks); **a check that CANNOT run for lack of its dependency (no served site, no `drush`) is unresolved → fail-closed HALT** — apply step 8 rule 2's unresolved-gate posture (an unknown gate result is fail-closed, never absorbed into a pass), never a silent "skipped → pass". **ALL adopted recipes' verifiers must pass** — the review is not green until every one does. Update each element's `verifier` field (`{ran, verdict, failed_checks}`) via `${CLAUDE_PLUGIN_ROOT}/scripts/gate-audit-write.sh "<task_folder>" agentic-recipe "<payload>"` (schema_version `1.5`; `references/gate-audit-schema.md` §5.13). **`gate-audit-write` overwrites the whole file** — first Read the existing `_agentic-recipe.json` and **read-merge-write the FULL `recipes[]` list**, preserving every element's decision half (`capability`/`recipe_name`/`recipe_sha`/`provenance`/`verified`/`decision`/`reason`/`body_path` from `/research`) and setting only each adopted element's `verifier`. Do not write a payload that drops any element or its decision half. **Fold the verifier outcome into `gates_run[]` so it reaches `overall_verdict` (the sidecar alone does NOT gate the review).** Add ONE aggregate **hard-block** entry to the step-4 `gates_run[]` skeleton — `name: "agentic-verifier"`, `kind: "hard-block"` — whose `verdict` is `"pass"` only if **every** adopted recipe's verifier passed, `"fail"` if **any** verifier failed, and an **unresolved** `"skipped"` + `unresolved: true` in `messages[]` if any verifier could-not-run (no served site / no `drush`). It flows through step-8 aggregation exactly like the other hard-block gates: a `fail` ⇒ `overall_verdict: fail` (step 8 rule 1), an unresolved verifier ⇒ fail-closed `overall_verdict: fail` (step 8 rule 2) — driving the step-9 prompt (or, under `--headless`, the non-zero exit). Keep the per-recipe detail in the sidecar too. **Emit this `gates_run[]` entry only when ≥1 adopted recipe exists** — no adopted recipe ⇒ no `agentic-verifier` entry (never a false gate). **Additive** — it never softens or replaces the hard-block gates below; an adopted recipe is not "done" until its own verifier passes. Skip silently (no verifier run, no `gates_run[]` entry) when there is no adopted agentic recipe (`recipes: []` / all `used_own`/`deferred` / absent).

   **5.0c Mechanism-challenge assertion gate (v5.17.0+, GAP G — `references/mechanism-challenge.md` for full semantics). Fail-closed; ALWAYS emits (unlike 5.0b).** Read `<task_folder>/_mechanism-challenge.json` and add ONE aggregate **hard-block** `gates_run[]` entry `name: "mechanism-challenge"`: `pass` iff the record exists AND `challenge_ran==true` AND no unresolved attended-supersede; an **absent** record ⇒ `skipped`+`unresolved:true` ⇒ fail-closed (step-8 rule 2); an unresolved supersede ⇒ `fail` (rule 1). Folds into `overall_verdict` like every hard gate. "No record" is the failure, not a skip — `/review` refuses to go green unless the mechanism was actually challenged. A per-mechanism `disposition: "unresolved"` (`mechanism-disposition.sh`'s `not_searched` path, meaning the cascade never ran for that one mechanism) is invisible to the rule above, and must stay that way: it does NOT fail this gate and does NOT block.** The kernel's own comment explains why: blocking here would halt the majority of a design phase's mechanisms, most of which (a `ddev restart`, a config toggle) have no native pattern to look for because they are not design decisions, and a gate that stops a person that often gets bypassed. The record still exists and `challenge_ran` is still `true`; only the honesty of what was actually checked changes. Count it instead: `unresolved_count` = the number of `mechanisms[]` entries with `disposition == "unresolved"`, out of `mechanisms_total` = `mechanisms[].length`. Surface both in the dedicated `{{mechanism_unresolved_line}}` (step 13), **not** folded into this entry's `gates_run[].messages[]`. `messages[]` is free-text per gate that gets reworded release to release, and this repo already has a stronger precedent for a per-gate count that has to stay comparable across runs: step 13's `spec_verdict_line` reads `<N>`/`<M>` straight off `_spec.json`'s array lengths rather than a sentence. A dedicated line keeps the count in one place with one format, which is the same reason those counts live there instead of in prose. This is also the fix for the defect that motivated it: an aggregate rule keyed only on unresolved *supersedes* structurally cannot see the mechanisms where no supersede was ever looked for, so without this count a reader has no way to tell "search ran, found nothing" from "search never ran," the exact confusion `grounding: none` used to cause, now moved one layer up into `/review`'s own summary.

   **5.0d Spec-axis review — does the change implement what was asked? (v5.20.0+, M2 — borrows mattpocock/skills' `code-review` two-axis idea; full contract `references/spec-axis-review.md`).** Standards (5.0/5.0b/5.0c above plus the hard-block battery in 5a/6) answers "does the code follow the repo's standards?"; Spec answers the orthogonal question "does the change faithfully implement what the originating task's contract actually asked for?" — **the two axes are never merged into one score**, so a change can pass every Standards gate and still surface a Spec fail. Read `<task_folder>/alignment.md`'s Task-Level `### Success criteria` (`references/alignment-contract.md`) plus `architecture.md` if present, and dispatch `ai-dev-assistant:spec-axis-reviewer` (Task tool, generic — same injected-context pattern as `architecture-validator` at 5.0) with the criteria and **the step-4 change set** (`files[]` from `review-change-set.sh`, which includes uncommitted work) to judge **(a) missing requirements** — a success criterion with no corresponding implementation — and **(b) scope creep** — substantive diff hunks untraceable to any criterion or architecture decision (generalizing `wo-critic`'s `meets-ac` lens from one work-order to the whole change). **Verdict rule — missing-requirements hard, scope-creep advisory:** `verdict` is `fail` **iff `missing_requirements[]` is non-empty** (the objective, hard signal — drives `overall_verdict` via step 8 rule 1 unchanged); `scope_creep[]` alone never fails the gate — a scope-creep-only result (`missing_requirements: []`, `scope_creep` non-empty) is `pass`, with the scope-creep findings surfaced as warnings in the rendered `## Spec` block. Deliberate de-risking of scope-creep's inherently subjective judgment under `--headless` autonomy (full rationale `references/spec-axis-review.md`). **Hand it an output path and read the verdict off disk (v5.35.7+):** tell it to write its sidecar to `<task_folder>/_spec-axis.json` and take `verdict` / `missing_requirements[]` / `scope_creep[]` from that file as scalars, never from its prose — the same truncation that hit `architecture-validator` at 5.0 hits the long verdict here, which is a list of every unimplemented criterion. **An absent sidecar is `no_return`:** record it in `_spec.json` as `verdict: "skipped"` with `skip_reason: "spec_axis_reviewer_no_return"` **and `unresolved: true` in `messages[]`**, so step 8 rule 2 fails closed. It is never a `pass` — `pass` is the claim "I looked and nothing is missing", and nobody looked. Verdict `pass | fail | skipped`; write `<task_folder>/_spec.json` via `gate-audit-write.sh <task> spec <payload>` (`gate-audit-schema.md` §5.15) and add ONE `gates_run[]` entry `name: "spec"`, `kind: "hard-block"` — it folds into step 8's `overall_verdict` exactly like any other hard-block entry (a `fail` triggers rule 1) while staying independently attributable, never collapsed into the Standards battery's aggregate signal. **An empty change set** ⇒ `verdict: "skipped"` with the `empty_reason` in `messages[]` when that reason is `no_changes_anywhere`; never `fail`. A reviewer handed no diff finds every criterion unimplemented and hard-fails a task that may be complete, which is what happened before the change set included the working tree. **No `alignment.md`** ⇒ `verdict: "skipped"` with a `messages[]` reason (never fabricate criteria) — a benign, non-`unresolved` skip like `skipped-not-shipped`, so it does NOT trip step 8 rule 2's fail-closed path. **Under `--headless`:** no prompt — a Spec `fail` is fail-closed exactly like every other hard-block gate (non-zero exit; appears in the compact per-gate verdict line).

   **5.0e Internal prior-art assertion gate (v5.26.0+). Fail-closed; ALWAYS emits. Full semantics: `references/internal-prior-art.md` (the `/review` assertion section) — do not restate them here.** Read `<task_folder>/_internal-prior-art.json` (`references/gate-audit-schema.md` §5.16) and add ONE aggregate **hard-block** `gates_run[]` entry `name: "internal-prior-art"`. It asserts the search **ran and was recorded**, never that it found anything: a source that could not be searched **passes** with its `skip_reason`, because making degradation a failure pushes a run toward fabricating a clean result. An **absent** record post-feature ⇒ `skipped`+`unresolved:true` ⇒ fail-closed (step-8 rule 2) — "nobody looked" must never read as "nothing was found"; a pre-feature task is a benign `skipped`+`skip_reason` like the `spec` gate's no-`alignment.md` path. An admissible **supersede** whose `migration_resolution` is null (neither an in-task decision nor a linked follow-up task) ⇒ `fail`. Under `--headless`, no prompt; fail-closed like every other hard gate.

   **5.0f Build-critique assertion gate (v5.33.0+). Fail-closed; ALWAYS emits. Was this build ever challenged by something other than the context that built it?** Run `${CLAUDE_PLUGIN_ROOT}/scripts/build-critique-assert.sh "<task_folder>" --change-set-file <path to step 4's saved review-change-set.sh JSON>` (Bash), adding `--change-set-empty` when step 4 reported `empty_reason: no_changes_anywhere`. **Save step 4's output to a file and pass it here** — the gate compares the record's `build_identity` against the change set you are actually judging, and a gate handed no change set cannot tell whether the critics ever saw this code, which is `unresolved` and fail-closed. This is what the `[r]` remediate branch makes routine: `[r]` means exit, fix, re-run, so every remediation produces a build the record predates, and without this comparison the re-run reads the pre-remediation record and passes. and add ONE aggregate **hard-block** `gates_run[]` entry `name: "build-critique"`, `kind: "hard-block"`, mapping the script's verdict through unchanged: `pass` → `pass`; `fail` with `unresolved:false` → `fail` (rule 1); `fail` with `unresolved:true` → `skipped` + `unresolved:true` in `messages[]` (rule 2, fail-closed); `bypassed` → `bypassed` carrying the script's `bypass_reason` (rule 3); `skipped` → a benign skip, never `unresolved`. Copy its `messages[]` across so the table says which build path was found and what was missing. **The script reads disk and this command does not second-guess it.** A task reaches Phase 4 by one of two build paths owing different records: an in-session `/implement` build owes `<task_folder>/_build-critique.json`, a `/run-work-orders` build writes `work-orders/wo-NN._critique.json` per work-order and owes none. It tells them apart by looking for those files, **and a build with neither was not challenged — a `fail`, not a skip.** Until v5.33.0 the whole enforcement was a `conditional` row in `phase-records-check.sh` plus a sentence of prose nothing evaluated, so a phase that skipped the rung read as complete and a record saying `verdict:"critical"` changed nothing about whether the task shipped; there is deliberately no path from "could not tell" to `pass`. **A record that IS present fails too** on `verdict:"critical"`, any component `blocking:true`, `verdict:"unresolved"`, a payload missing `components_declared`/`components_critiqued`/`uncritiqued[]` (a partial run that cannot say what it did not look at), a `skipped` with no reason, or zero components critiqued against a non-zero declared count. The one way past is a `bypass_reason` recorded in the record itself, surfaced in the table and driving `overall_verdict:"bypassed"` with `pr_ready:false`; there is **no `--skip-build-critique` flag** — like 5.0c and 5.0e the override lives on disk where an auditor reads who took it. The record's own `alignment.verdict` is surfaced, never blocking here: 5.0d judges that question against the current change set, and blocking on the Phase 3 copy as well would report one problem twice.

   **5a. Change-scoped gate passing (default) and `--full-audit`.** The four PHP/JS-centric gates (`tdd` / `solid` / `dry` / `security`) accept a `--files <list>` parameter (forwarded from their `validate-*` wrappers) which passes to the underlying code-quality `--changed <list>` mode — scoping each gate to the diff rather than the whole project tree.

   **Default (change-scoped) — all modes except `--full-audit`:** From the **step-4 change set** (`files[]`, which includes uncommitted work — a code file edited and not yet committed is still what these gates exist to check), filter to gate-relevant extensions. The extension set is the **union** of a framework-neutral language floor (`.php` `.js` `.mjs` `.cjs` `.ts` `.tsx` `.vue`) **and** the active framework's code-quality extensions, reconstructed from the **same review recipe body already Read at step 5.0** (no second resolution): for each `available:true` framework, take its `## Code-quality extensions` declaration (the `code_quality_extensions` JSON list) and add those to the filter. No recipe (or a framework declaring none) → neutral floor alone (an undeclared framework file type is simply not scoped in — agnostic-floor posture). Write the filtered list to a temp file and pass it via `--files <tmpfile>` to each of the four wrappers (`validate-tdd`, `validate-solid`, `validate-dry`, `validate-security`); clean it up after. An empty filtered list (CSS/config/asset-only change) is skipped internally by the code-quality `--changed` mode — **not** a `--skip-<gate>` bypass (no `bypass_reason`), so by step-8 rule 5 it does **not** prevent `overall_verdict: pass`. **`--full-audit` mode** skips the diff-filter entirely and invokes all four gates with **no** `--files` (whole-tree scan, pre-v4.20 behavior — surfaces whole-codebase debt). `guides` is **not** covered here (own applicability check; CSS/SCSS/design-system changes ARE applicable and cite the guide); `validate-playbook-adherence` / `skill-review` / `plugin-validate` keep their own conditions; an empty diff → empty list → each skips cleanly.

6. **Change-impact dispatch** (v4.11.0+ — replaces v3.13.0's always-soft visual step). Execute `references/visual-review/change-impact-dispatch.md` in full — a RECOMMENDER, not an enforcer. Fast path: no `**Visual Review:**` field in `project_state.md` (or `disabled`) → run zero new gates, print `no visual-review surfaces configured; run /setup-* to opt in`, omit `dispatch_plan` from the payload entirely, skip to step 7. Otherwise: `change-impact-classify.sh <task> --files-from <step-4 change set>` classifies it → recommended gates. **Pass the change set explicitly** — left to itself the script diffs `main..HEAD`, which is both the wrong base on a non-`main` branch and blind to uncommitted work; the user opts in **per task** via a `## Review Gates` block in `task.md` (written once, never re-asked); opted-in **and** dispatch-ready gates run soft; `visual_parity` auto-runs on design-implementation tasks; unshipped B/C/D gates → `skipped-not-shipped`. `--include-/--skip-<gate>` override the stored opt-in for this run only. Assemble `dispatch_plan` (`gate-audit-schema.md`) for the step-10 payload.

7. **Apply `--skip-<gate> <reason>` flags.** Validate gate name against whitelist + reason non-empty + reason not `--`-prefixed (else exit 2). For each valid flag: don't run the gate; set `gates_run[].verdict: "bypassed"` and `bypass_reason: <reason>`.

8. **Aggregate `overall_verdict`.** A per-gate parse error or missing/unreadable envelope is an **unresolved** result — record it `verdict: "skipped"` with `unresolved: true` in `gates_run[].messages[]`, **distinct** from an explicit `--skip` bypass and from `skipped-not-shipped`. The Spec axis (5.0d) folds in as one more named hard-block `gates_run[]` entry (`name: "spec"`) — a Spec `fail` triggers rule 1 like any other, and its no-`alignment.md` `skipped` state is a `skipped-not-shipped`-shaped benign skip (never `unresolved`), so it never forces rule 2's fail-closed path; either way it stays attributable to its own name, never collapsed into the Standards battery's aggregate signal. Resolve in this order; **every branch yields a legal `overall_verdict` ∈ {pass, fail, bypassed}, and the five rules are exhaustive over the `verdict` enum** — a value with no rule is the defect rule 4 closes:
   1. `fail` if any hard-block gate has `verdict: fail` — **fail dominates** (a real fail is never masked by another gate's explicit `--skip`).
   2. `fail` if any hard-block gate is **unresolved** (parse-error / missing envelope) — an unknown gate result is **fail-closed, never absorbed into `bypassed`**. (Only the **`overall_verdict`** is written `fail`; the gate's own per-gate `verdict` stays `skipped` + `unresolved: true`, with a `messages[]` note — the schema enum has no `incomplete` value.) **This rule is ranked ABOVE bypass on purpose.** A gate's own envelope may also declare itself unresolved: when `validations/latest/<gate>.json` carries `unresolved: true` in its `messages[]`, propagate that into this gate's `gates_run[]` entry and apply this rule. That is how a wrapper reports "I was invoked and could not actually check anything" (the TDD gate's no-test-executed path), which is a different fact from a clean skip and must not be absorbed into one.
   3. `bypassed` if any hard-block gate has `bypass_reason` populated (explicit `--skip-<gate>`, or a documented auto-bypass such as an unshipped `validate-playbook-adherence`) — reached only when there is no `fail` and nothing unresolved.
   4. `fail` if any hard-block gate carries the literal `coverage_partial: true` in its `messages[]` — the marker a wrapper emits when it downgraded to `warning` because an analyzer was absent, crashed, or had nothing to read. **Keyed on the marker, never on `verdict: "warning"`.** `warning` is overloaded and usually means a fully measured run with a mildly bad number: duplication over the 5% target (`dry-check.sh`), more than ten SOLID warnings (`solid-check.sh`). Failing those would block projects where every tool IS installed, for findings that never blocked before, and would teach everyone to reach for `--skip-dry` — the bypass that makes this whole fix worthless. Part-measured is a coverage fact, not a findings one, and only the coverage fact fails here. `overall_verdict` offers only {`pass`, `fail`, `bypassed`}; `bypassed` means a human recorded a reason, so `fail` is the one left, and it routes to step 9 where `[s]` records that reason. Ranked below bypass: this is a KNOWN result, so an explicit bypass may absorb it, unlike rule 2's unknown. Before v5.35.6 `warning` had no rule at all and aggregation fell off the end of this list.
   5. `pass` if every hard-block gate is `pass` or a benign non-blocking state (`skipped-not-shipped`, a no-`alignment.md` Spec skip, an empty-diff internal skip, **and an ordinary `warning` from a fully measured gate** — findings under the fail threshold have never blocked and still do not). Benign means **not** unresolved, **not** carrying `coverage_partial: true`, **not** a hard-block fail; those states do not prevent `pass` or force non-zero on their own. A `messages[]` line beginning `coverage_gap_nonblocking:` is one such benign state and MUST still be rendered in the `## Gates` table and carried into `_review.json`: it names layers that did not run and that the project has no way to close: host binaries `install-tools.sh` cannot place (`tool-catalog.json` scope `machine`, which DO block under `CI`), and layers with nothing to install at all (`layers[]` `builtin`/`optional-contrib`, which `CI` does not change). The message states which applies per name; do not restate one reason for all of them — not blocking is not the same as not reporting, and dropping it hides a real gap. v5.35.6+: a gate's `verdict` and its `coverage_partial` marker are INDEPENDENT — a `fail` carrying the marker is still a `fail` and still triggers rule 1, never softened to `warning` by the gap beside it. The two that are NOT benign, spelled out so nobody re-derives them: a gate that measured nothing because its analyzer was absent is `unresolved` and rule 2 fails closed, and a gate that measured only part of its ground carries `coverage_partial: true` and rule 4 fails. Neither is a finding about the code; both are facts about what was looked at.

8b. **Did the contract move while the review ran? (v5.35.5+)** Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/contract-baseline.sh" diff "<task_folder>" --slot review` (Bash) after every gate reports, before aggregating; record it as step 10's `contract_drift` (`checked: false` with a reason if step 0 did not capture). Never blocking on its own. **One consequence is not advisory:** `alignment.md` in `changed[]` means the Spec gate judged a criteria list no longer on disk — **Re-run 5.0d**, or its `gates_run[]` entry becomes `skipped` with `unresolved: true`, which step 8 rule 2 treats as fail-closed. A stale verdict must not be reported as a current one.

9. **On `overall_verdict == "fail"` (per step 8, fail dominates any coexisting `--skip` bypass): mandated-wording prompt.** Display verbatim per template `review-gate-fail` (literal text below; mirrors v1.2 template when sibling ships, byte-identical fallback otherwise). Block on `[r]/[s]/[a]` — no default. `[r]` exits 1 (user fixes, re-runs). `[s]` prompts per failed gate for free-text reason, populates `bypass_reason`, sets `overall_verdict: "bypassed"`. `[a]` exits 1 without writing `_review.json`. **Non-`r/s/a` input: re-display the prompt verbatim. Do not infer choice.** **Under `--headless`:** do NOT display this prompt — fall straight through to step 10 with `overall_verdict: "fail"`, then **print the compact verdict line (Headless mode) and exit non-zero**. **Fail-closed: never auto-`[s]`/auto-bypass.** A bypass under `--headless` requires an explicit `--skip-<gate> <reason>` on the invocation (step 7).

9a. **Remediating after `[r]` — one mutable working tree per agent (v5.35.7+).** `[r]` means exit, fix, re-run, and the fix is normally more than one agent. **Concurrent remediation agents must not share a mutable working tree.** Observed live on this branch's own defects: a mutation-testing verifier and a test-author were dispatched against the same source file at once, and three things went wrong — the orchestrator inspected the verifier's live mutation (`if (FALSE)` inserted into a guard) and reported it as the frozen clean state; the verifier's backup predated the author's edit, so restoring it would have silently reverted work the tests already asserted; and a passing test run had to be retracted because a mutation landed inside its window. Two of the dispatched agents flagged the contention before the orchestrator did. Use the mechanism that already exists rather than a second one: give each concurrent agent its own tree with `/ai-dev-assistant:worktree`, which is the same ephemeral-worktree-per-unit discipline `skills/work-order-loop-parallel/SKILL.md` runs the parallel conductor on (one worktree per batched work-order off a single round base, and batches selected so their declared files are **pairwise disjoint**). An agent that mutates-and-restores a file — a mutation-testing verifier is the case that bit — **owns that file exclusively** for its run: no other agent edits it, no other agent's test result is trusted while a mutation is live, and its backup is taken inside its own tree with `cp` (never `git checkout`, which discards uncommitted work belonging to somebody else). Sharing one tree is fine only when the dispatches are strictly sequential.

10. **Write `_review.json`** — **first preserve the pass it is about to replace.** Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/review-record-archive.sh" "<task_folder>"` (Bash) **before** the write: it copies an existing `_review.json` to `<task_folder>/review-rounds/_review-<n>.json` (oldest pass = 1, never overwriting an archive) and reports what it did. **If it exits non-zero, do NOT overwrite (v5.35.7+).** Non-zero means the outgoing record could not be preserved — an unwritable task folder, a copy that did not land, an archive that did not match the record it came from — and writing over it anyway is exactly the loss the script exists to stop. Surface its stderr verbatim, **skip the `_review.json` write, step 11's `PR_BODY.md` and step 12's Phase-4 mark**, still print the step-13 summary so this pass's gate verdicts are not lost with the record, and exit non-zero in every mode including `--headless`. Step 11 is named here because it does not test for this on its own: its condition is `pr_ready != true`, and `pr_ready` is computed in the write this branch skips, so a green pass would emit a PR body backed by no review record — which is the state `/complete` refuses. An unrecorded pass is a state an operator can see and fix; a silently destroyed one is not. A first pass is not this case: no existing `_review.json` is `archived: false` with `reason: "no_current_record"` and exit 0. `_review.json` keeps its meaning, its location and its field paths exactly — every consumer still reads `.gate_specific.overall_verdict` off the current record, and this adds no round budget, no delta-scoping and no control flow. It exists because `[r]` makes re-review routine: one live task ran FOUR passes, each overwrote the last, and the defect pass 3 found is in no surviving record. Then write via `gate-audit-write.sh <task> review "@<payload_file>"` — **write the payload to a file and pass it as `@<path>`**, because this record carries every gate's messages and detail and a command-line argument is capped at 128 KB by the kernel; past that the write fails with "argument list too long" before the script starts, and nothing in the script — validation, atomic rename, the key-loss guard — runs at all (atomic temp+rename; schema_version `1.2` for v4.11.0+ — the `review` payload schema grew the optional `dispatch_plan` key). When step 6's dispatcher ran, the payload carries `dispatch_plan` (`gate-audit-schema.md`); when visual review is not set up, the key is omitted. `gate_specific.pr_ready: true` ONLY when `overall_verdict == "pass"` AND not `--dry-run`. Bypass paths → `pr_ready: false` (user picked the bypass; they pick whether the PR is ready). Dry-run → `pr_ready: false` regardless. **Carry step 4's `head_upstream` and `base_distance` into `gate_specific` and print them on the `pr_ready` line — advisory, never blocking (v5.35.7+).** `head_upstream.configured: false` means the reviewed work exists on this machine only, so `pr_ready: true` is a statement about the gates and not about a pull request being possible; say so in one line (`head has no upstream; <base_distance.ahead> commit(s) ahead of <base>` / `<n> ahead, <m> behind <ref>`) and continue. Measured live: two feature branches with no upstream, one seven commits ahead of `origin/staging`, and every gate reasoned about them without noticing. A local-only branch is legitimate — being unable to tell is the defect — so this **must not** change `pr_ready`, `overall_verdict`, or any exit code. `gates_run[]` is the full hard-block set, regardless of how populated (rerun-failed merges previous-run passes with this-run reruns).

11. **Write `PR_BODY.md`.** Skip if `--no-pr-body` OR `--dry-run` OR `pr_ready != true` OR **step 10's archive aborted the `_review.json` write** — no record, no PR body. Template: H1 task title, Summary (Goal first paragraph), AC count `[x]`/total, gate verdicts table, audit links footer.

12. **Mark Phase 4 `[x]`** in `task.md` (only if not `--dry-run` AND `overall_verdict in ("pass", "bypassed")`).

13. **Display `review-summary` mandated wording** (literal text below). `gates_run_table` renders every `gates_run[]` entry **EXCEPT** `name:"spec"` — that entry renders ONLY on `spec_verdict_line`, never duplicated into the Standards table. `spec_verdict_line` format: `Spec: <pass|fail|skipped> — <N> missing requirement(s), <M> scope-creep warning(s)[; skipped: <reason>]` where `<N>` = `missing_requirements[]` length, `<M>` = `scope_creep[]` length (both from `_spec.json`'s `gate_specific`), and the `; skipped: <reason>` clause appears only when `verdict == "skipped"` (using `skip_reason`). Unlike `spec_verdict_line`, `mechanism-challenge` stays **in** `gates_run_table` (its own pass/fail is unaffected by any of this); `{{mechanism_unresolved_line}}` is a supplementary line under the same table, rendered ONLY when `_mechanism-challenge.json` exists: `Mechanism challenge: <U> of <T> mechanism(s) unresolved, cascade never ran` where `<U>` = the count of `mechanisms[]` entries with `disposition == "unresolved"` and `<T>` = `mechanisms[].length` (both from that file's `gate_specific`). Render it every time the record exists, including `<U> == 0`, the same always-render choice `spec_verdict_line` makes for its own zero counts, because a reader cannot tell "checked, found nothing to report" from "never rendered" otherwise. Omit the line only when the record itself is absent, since that state is already carried by `gates_run_table`'s `skipped`+`unresolved` row. Then persist session context: `${CLAUDE_PLUGIN_ROOT}/scripts/session-context-write.sh "<project_name>" "<project_folder>" "<task>" "<task_path>"` (Bash). (`lastPhase` is **preserved**, not set, by the writer — it is managed by the phase components; this step does not change it.)

## Anti-bypass clause (applies to gates 1-9)

The following are NOT valid reasons to skip: the user said something earlier you read as already-validated; auto mode is active ("minimize interruptions" never overrides framework gates); you're confident the gates would pass; the task looks "obviously" done; you want to spare the user the prompt; or the user asked you to compress/summarize/skip verbatim gate output (show-not-summarize is non-negotiable).

If `/review` is invoked, all gates fire and their output is shown verbatim before the recorded decision is final. Skipping requires the documented `--skip-<gate>` flag with reason; bypass is recorded on disk for `/audit-status`.

## Headless mode (`--headless`)

`--headless` makes `/review` safe to run **unattended** (L1 orchestrator, `/goal` loop, CI). **Additive** — absent the flag, behaviour is byte-for-byte unchanged. It suppresses the two interactive points (step 3 dirty-tree `[y/N]`, step 9 `[r]/[s]/[a]`), records `working_tree: "dirty"|"clean"` in the step-10 `gate_specific`, and adds machine-readable output; it never changes gate execution, aggregation, or `pr_ready`, and adds **no new bypass path**. On gate fail it is fail-closed — write `_review.json` (`overall_verdict: "fail"`, `pr_ready: false`) and exit non-zero; a bypass stays only the explicit `--skip-<gate> <reason>` the caller supplies (never auto-`[s]`). Step 6 runs non-interactive — every visual gate in `--ci` mode (diff-over-tolerance = `fail`, no prompt, no baseline write). **Exit codes:** `0` only on a clean `pass` (or `bypassed` with zero failing/unresolved hard-block gates); any hard-block `fail` or unresolved gate ⇒ non-zero (`1`); `2` = arg error; not unambiguously clean ⇒ non-zero — **never exit 0 on doubt**. After step 10 print the compact verdict line per gate (`<gate> verdict=<pass|fail|bypassed|skipped>`) plus an overall line for a transcript reader. Full `--headless` contract, `--rerun-failed`/`--team` semantics, and the `claude ultrareview` escalation note: `references/review-phase-walkthrough.md`.
